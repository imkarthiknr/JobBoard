## Prerequisites

| Tool                                   | Version | Needed for                      |
| -------------------------------------- | ------- | ------------------------------- |
| Python                                 | 3.11+ (`.python-version` pins 3.13) | Local development |
| [uv](https://docs.astral.sh/uv/)       | 0.5+    | Dependencies and virtualenv     |
| Docker + Compose v2                    | any recent | App + PostgreSQL in containers |
| PostgreSQL                             | 16      | Optional locally; SQLite works for development |

## Setup

```bash
git clone https://github.com/imkarthiknr/JobBoard.git
cd JobBoard
uv sync                          # creates .venv with app + dev dependencies (from uv.lock)
cp .env.example .env             # optional; defaults work out of the box
uv run alembic upgrade head
uv run python -m app.seed        # optional: demo user + 10 jobs
uv run uvicorn app.main:app --reload
```

- Web UI: http://localhost:8000
- Swagger UI: http://localhost:8000/docs (ReDoc at `/redoc`)
- Demo login: `demo` / `jobboard123`

Prefix commands with `uv run`, or activate the virtualenv (`source .venv/bin/activate` on macOS/Linux, `.venv\Scripts\activate` on Windows).

### Running against PostgreSQL

```bash
docker compose up -d db
DATABASE_URL=postgresql+psycopg://jobboard:jobboard@localhost:5432/jobboard uv run alembic upgrade head
```

The Compose `db` service doesn't publish its port by default. Add `ports: ["5432:5432"]` to it, or run everything with `docker compose up --build`.

## Configuration

Settings come from environment variables or a `.env` file (`app/core/config.py`, pydantic-settings). Names are case-insensitive.

| Variable                      | Default                         | Description                                      |
| ----------------------------- | ------------------------------- | ------------------------------------------------ |
| `DATABASE_URL`                | `sqlite:///./jobboard.db`       | SQLAlchemy URL. Use `postgresql+psycopg://…` for PostgreSQL |
| `SECRET_KEY`                  | dev-only placeholder            | JWT signing key. **Set this in any shared environment** |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `60`                            | Token and cookie lifetime                        |
| `COOKIE_SECURE`               | `false`                         | Mark the auth cookie `Secure` (enable behind HTTPS) |
| `SEED_DEMO_DATA`              | `false` (`true` in Compose)     | Docker entrypoint runs `app.seed` on start       |

`.env` is gitignored. Commit changes to `.env.example` instead.

## Database and migrations

The schema is managed with **Alembic** (`migrations/`). `migrations/env.py` reads `DATABASE_URL` from the app settings, so there is a single source of truth.

```bash
uv run alembic upgrade head                              # apply
uv run alembic revision --autogenerate -m "add salary"   # after changing a model
uv run alembic check                                     # fails if models ≠ migrations
uv run alembic downgrade -1
```

- Review autogenerated migrations before committing them. Alembic misses some changes, such as renames.
- Migrations must work on both SQLite and PostgreSQL. SQLite runs in batch mode (`render_as_batch`).
- `tests/test_migrations.py` upgrades a fresh database, runs `alembic check` and downgrades, so a model change without a migration fails the tests.

The Docker entrypoint runs `alembic upgrade head` before starting Uvicorn.

## Architecture

```
app/
├── main.py            create_app(): routers, static files, HTML-vs-JSON error handling
├── core/
│   ├── config.py      Settings (cached)
│   └── security.py    bcrypt hashing, JWT create/decode
├── db/                Base, engine, SessionLocal, get_db()
├── models/            User 1─* Job (cascade delete)
├── schemas/           Pydantic models: validation + response shapes
├── services/          users.py, jobs.py: queries and rules, no FastAPI imports
├── api/
│   ├── deps.py        DbSession, OptionalUser, CurrentUser
│   └── routes/        auth, users, jobs (mounted at /api/v1)
└── web/
    ├── routes.py      HTML pages + form handling
    ├── templates/     Jinja2 (base, jobs/*, auth/*, error)
    └── static/        CSS, favicon
```

Design decisions:

- **One service layer, two front doors.** The JSON API and the HTML UI both call `services/`, so ownership, visibility and search rules are written once and tested once.
- **Pydantic schemas validate both front doors.** The web routes run form input through the same `JobCreate` and `UserCreate` models and translate the errors into friendly, per-field messages.
- **Dependency-injected sessions.** `get_db` is a FastAPI dependency, and tests override it to use an isolated database.
- **Typed SQLAlchemy 2 models** (`Mapped[...]`), with indexes on the search and filter columns (`location`, `is_active`, `date_posted`, `owner_id`).
- **Search** uses `ILIKE` with escaped wildcards, which is portable across SQLite and PostgreSQL. A `tsvector` index is on the roadmap.

## Security notes

- **Passwords**: bcrypt with a per-password salt. Input over 72 bytes is rejected rather than silently truncated. Login compares against a dummy hash when the user doesn't exist, so response timing doesn't reveal which usernames are registered.
- **Tokens**: HS256 JWTs with `sub`, `iat` and `exp`. The API takes them from `Authorization: Bearer`. The web UI keeps the same token in an `HttpOnly`, `SameSite=Lax` cookie (`Secure` when `COOKIE_SECURE=true`).
- **CSRF**: every state-changing UI action is a `POST` form, and `SameSite=Lax` stops browsers from sending the cookie on cross-site POSTs.
- **Open redirects**: `?next=` after login only accepts local paths.
- **XSS**: Jinja2 auto-escapes all output. Job descriptions are plain text, rendered with `white-space: pre-line`.
- **Authorization**: only the owner or a superuser can edit or delete a job. Closed jobs return `404` to everyone else.
- **Secrets**: never commit `.env`. Generate a key with `python -c "import secrets; print(secrets.token_urlsafe(32))"`.

## Testing

```bash
uv run pytest                  # 46 tests, in-memory SQLite
uv run pytest -k web -x        # just the UI tests, stop at first failure
TEST_DATABASE_URL=postgresql+psycopg://jobboard:jobboard@localhost:5432/jobboard_test uv run pytest
```

| File                   | Covers                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------ |
| `test_users_api.py`    | Registration rules and conflicts, login, inactive users, token checks                           |
| `test_jobs_api.py`     | CRUD, validation, search/filter/pagination, wildcard escaping, ownership, superuser, closed-job visibility, cascades |
| `test_web.py`          | Pages, search, HTML escaping, 404 page, register/login/logout, cookie flags, open-redirect guard, form errors, owner-only actions |
| `test_security.py`     | Hashing, token expiry and tampering                                                              |
| `test_migrations.py`   | Migrations upgrade, match the models, and downgrade                                              |

How the fixtures work (`tests/conftest.py`):

- `db` creates all tables before each test and drops them afterwards, which gives full isolation.
- `client` is a `TestClient` with `get_db` overridden to that session.
- `make_user(...)` and `token_for(client, username)` cut setup boilerplate.

## Code style

- **Ruff** handles linting and formatting (config in `pyproject.toml`, 100-column lines): `uv run ruff check --fix . && uv run ruff format .`
- `.editorconfig` and `.gitattributes` keep files LF in the repository, so Windows checkouts don't show whole-file diffs.
- Commits follow [Conventional Commits](https://www.conventionalcommits.org/).

| Lint             | `ruff check`, `ruff format --check`                                            |
| Tests · SQLite   | pytest on Python 3.11 and 3.13                                                 |

## Common tasks

**Add a field to jobs (e.g. `salary_range`)**

1. Add the column to `app/models/job.py`.
2. Run `uv run alembic revision --autogenerate -m "add salary range"` and review the result.
3. Add the field to `JobCreate`, `JobUpdate` and `JobRead` in `app/schemas/job.py`.
4. Add the form field (`jobs/form.html`), display it (`jobs/detail.html`) and update `docs/API.md`.
5. Add tests.

**Make a user a superuser**

```bash
uv run python -c "from app.db.session import SessionLocal; from app.services.users import get_by_username; \
db=SessionLocal(); u=get_by_username(db,'alice'); u.is_superuser=True; db.commit()"
```

**Reset local data**: delete `jobboard.db` and run the migrations again, or run `docker compose down --volumes`.

## Troubleshooting

| Symptom                                                   | Fix                                                                                 |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `no such table: jobs` / `relation "jobs" does not exist`  | Run `uv run alembic upgrade head` against the same `DATABASE_URL`.                  |
| Logged out after a restart                                | `SECRET_KEY` changed, which invalidates existing tokens. Set a fixed key in `.env`. |
| Login works over HTTP locally but not in production       | Behind HTTPS, set `COOKIE_SECURE=true`. Behind a proxy, keep `--proxy-headers`.     |
| `psycopg.OperationalError: connection refused`            | PostgreSQL isn't running, or the host/port in `DATABASE_URL` is wrong.             |
| `alembic check` fails in CI                               | A model changed without a migration. Autogenerate one.                              |
